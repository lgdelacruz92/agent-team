# Frontend controller: current understanding

Estimated reading time: 3 minutes (150 WPM)

The frontend controller is a **deterministic dispatcher for an AI engineering team**.

The CTO decides what needs doing and whether the result is acceptable. The controller decides when a ticket can run and which worker gets it. The worker does the engineering.

## The intended flow

Using the [scheduler sketch](../../../../playground/publisher-consumer-pattern.md) as the target:

1. Read the Vikunja board and check work already in progress.
2. For each running ticket, check its worker and session: finished, stale, stuck, or unreachable.
3. Put finished work in Review. Retry failed work, distinguishing a worker outage from a task failure.
4. Find Ready and Retry tickets whose blockers are Done.
5. Match those tickets to available workers by skill and start as many as possible.
6. Keep enough information on the board to recover after a controller restart.

The OS analogy fits: **tickets are processes, workers are CPUs, and the controller is the scheduler.** The board is both the queue and the shared record of what’s happening.

## Where the code is today

It has the **dispatch skeleton**:

- Reads Ready and Retry tickets from Vikunja.
- Finds an available worker, starts a session, sends the ticket prompt, and moves the ticket to In progress.
- Remembers the latest session ID per worker on disk.
- Provides pause, resume, status, and manual tick endpoints.
- Has agent methods for checking completion and staleness, plus session cleanup methods.

It doesn’t yet have the full supervision loop. The scheduler doesn’t check whether a ticket finished, post its report, move it to Review, retry failures, or clean up sessions. `isProgressing()` is currently a placeholder.

## Biggest gaps between the sketch and code

- **Restart recovery:** The sketch puts worker and session IDs on the ticket. The code saves only `worker → session` locally; it doesn’t restore the ticket-to-worker relationship or resume watching that run.
- **Selection:** The sketch checks blockers for both Ready and Retry and prioritizes Retry. The code checks Ready for any listed blockers, takes Ready first, and doesn’t check Retry blockers.
- **Worker matching:** Workers have skills, but the scheduler doesn’t match them to tickets yet. One worker is wired up in `index.ts`.
- **One tick:** The sketch can start several tickets per pass. The code starts at most one per tick.
- **Status and dry run:** `/status` is mostly a placeholder. `CTR_DRY_RUN` currently changes the startup message, but doesn’t stop dispatch.

## Takeaway

The direction is a **traffic controller for AI workers, not another AI manager**. The controller’s value is reliably moving work through the lifecycle without making the CTO or a human babysit every session.

The biggest next piece is connecting **“started a ticket” to “observe and finish that same ticket”**, including after a restart. Right now, dispatch works further than the lifecycle around it.
